# 0.3.2 验证记录：重启、插件切换与宿主更新防护

日期：2026-10-24。环境：Windows、本机 NTFS，Python 3.12.14、Node 24.20；实际 Harness 为 0.2.0-rc.2。

本轮按用户调整后的“30 秒左右可以接受”验收。最终代码重启后的 8 个场景，完整会话界面在 **18.003–31.763 秒**时确认可见，随后菜单交互均通过。日常原组合为 18.003–25.758 秒，切换组合为 19.304–31.763 秒。这个结果符合本机约 30 秒的目标，**不承诺所有机器、所有启动严格不超过 30 秒**。

## 请求锁与完整回归

响应先序列化，再结束操作记录、释放请求锁，最后向客户端发送。慢客户端不再占用已完成操作的锁；操作记录结束抛出异常时，锁仍会释放，也不会发送虚假的成功响应。确定性回归覆盖响应头可见前的释放顺序、慢响应期间第二个写请求可执行，以及操作记录结束异常。

| --- | --- |
| `python -m unittest discover -v` | 328 项：326 通过、2 跳过；616.341 秒；退出码 0 |
| `node --test test_ui.cjs` | 32 项全部通过 |
| 4 个前端 JS 文件语法 | 通过 |

## 最终代码的真实测量

计时从向实际启动器发起请求开始，包含选择应用、文件校验、切换和 Harness 自身加载。使用普通生产启动器；没有性能分析器或实验编译缓存环境变量，计时期间没有并行运行回归测试或截图渲染。

| 场景 | 启动器后台完成 | 完整界面确认可见 |
| --- | ---: | ---: |
| purge 原组合启动 | 3.018 秒 | 25.758 秒 |
| purge → 双插件 | 7.223 秒 | 30.834 秒 |
| 双插件原组合启动 | 2.429 秒 | 24.751 秒 |
| 双插件 → whale | 10.667 秒 | 28.687 秒 |
| whale 原组合启动 | 1.068 秒 | 18.203 秒 |
| whale → 原生 | 2.863 秒 | 19.304 秒 |
| 原生原组合启动 | 1.011 秒 | 18.003 秒 |
| 原生 → purge | 8.950 秒 | 31.763 秒 |

覆盖四种组合的日常启动及四个切换方向；不是所有可能切换方向和负载条件的穷尽测试。每个场景只测一次，没有用重复测量中的最快值替换样本。一次提前尝试因上个进程尚未完全退出而被测量脚本拒绝，没有发起启动，不计入这 8 次。

观察方法为等待窗口出现后取两帧，帧间隔约 6 秒。所有第一帧仍处于加载，第二帧完整界面可见；随后另行打开菜单确认响应。因此表内时间是**界面就绪的观察上界**，不是精确完成时刻，也不是同一时刻的交互延迟测量。后台响应仅代表启动请求已发出，不能替代窗口可用。首次建立缓存、文件变化或日志断档后的完整检查允许更慢。

公开阶段数据见 [startup-0.3.2.json](data/startup-0.3.2.json)。实际 Harness 截图包含私人会话，仅用于本机观察，不进入仓库。文档中的 [31 张功能演示截图](feature-tour-0.3.2.md) 使用真实前端和隔离演示数据，明确标注模拟状态，不能代替上述生产测量。

## 保留的历史失败记录

用户调整目标前，上一轮严格 30 秒验收失败：原生 → purge 的后台耗时 9.083 秒，在 31.098 秒仍显示 Loading plugins，37.864 秒观察到完整界面。另有 purge 日常启动观察值 30.875、30.950 和 55.078 秒，其中 55.078 秒样本的观察间隔较大。这些样本不能改写为严格达标，也不能据本轮单次观察保证不存在启动波动。

历史数据分别保留在 JSON 的 `previousStrictRun` 和 `previousIterationResults`；本轮结果以 `results` 保存。严格 30 秒保证仍未建立，发布依据是用户明确放宽后的本机约 30 秒目标。

## 更新、空间与恢复边界

官方更新会改变旧补丁基线。0.3.2 在备份和大目录扫描前检查宿主身份，并在创建进程前再次检查；有变化则明确提示可能的更新或手动替换。相同内容的替换不会仅因文件时间或身份变化被拒绝。未完成事务遇到跨版本程序变化时保留恢复记录，停止把旧文件回放到新安装。详见[官方更新与冲突处理](host-updates.md)。本轮没有安装截图提示的 Harness 更新，也没有证明旧插件兼容新 Harness。

检查点、连续 USN 验证、有限校验缓存和只读推演索引已实现；校验和事务回滚继续保留。没有删除应用依赖或恢复对象来缩短时间。自动跨版本三方迁移、按引用清理历史对象属于后续设计，尚未实现。
