# 0.3.2 验证记录：重启、插件切换与宿主更新防护

日期：2026-10-24。环境：Windows、本机 NTFS，Python 3.12.14、Node 24.20；实际 Harness 为 0.2.0-rc.2。

本页的 8 次窗口计时对应 `bcb8a28` 的性能验收版本，作为历史证据保留。随后新增的官方更新、插件更新与安装会话保护另见[补充验证](update-validation-0.3.2.md)，不把这些旧计时冒充新改动的测量。

本轮按用户调整后的“30 秒左右可以接受”验收。最终代码重启后的 8 个场景，完整会话界面在 **15.115–35.318 秒**时确认可见，随后菜单交互均通过。日常原组合为 15.115–35.318 秒，切换组合为 18.276–32.973 秒。按本机约 30 秒的目标报告这些观察值，**不承诺所有机器、所有启动严格不超过 30 秒**。

## 请求锁与完整回归

响应先序列化，再结束操作记录、释放请求锁，最后向客户端发送。慢客户端不再占用已完成操作的锁；操作记录结束抛出异常时，锁仍会释放，也不会发送虚假的成功响应。确定性回归覆盖响应头可见前的释放顺序、慢响应期间第二个写请求可执行，以及操作记录结束异常。

完整 CI 结果见 [GitHub Actions](https://github.com/schrieeeffer/harness-launcher/actions/runs/40098542189)，对应生产代码 `bcb8a28`，之后只更新文档。此前本机完整回归为 328 项、326 通过、2 项符号链接权限跳过；第一轮 CI 随后暴露快速连续改写导致文件时间戳碰撞的真实问题，不能以那次本机通过宣称最终代码正确。

最终修复为文件缓存增加当前日志身份和文件 USN，在新内容进入缓存前建立 CLOSE 屏障，并使文件缓存和目录检查点格式 1、2 失效。新回归固定时间字段、保留真实 USN 与遗留属性句柄，稳定验证同时间戳改写不会误命中；另测日志身份变化和关闭屏障失败，没有通过增加延时或放宽断言掩盖问题。

原校验与回滚用例继续覆盖文件变化、缓存失效、USN 断档、未关闭句柄、失败恢复和启动失败；12 项宿主更新用例覆盖 EXE/ASAR 变化、相同内容替换、旧暂存归档遮蔽、提交前后更新与跨版本回滚保护。

## 最终代码的真实测量

计时从向实际启动器发起请求开始，包含选择应用、文件校验、切换和 Harness 自身加载。使用普通生产启动器；没有性能分析器或实验编译缓存环境变量，计时期间没有并行运行回归测试或截图渲染。

| 场景 | 启动器后台完成 | 完整界面确认可见 |
| --- | ---: | ---: |
| purge 原组合启动 | 2.643 秒 | 35.318 秒 |
| purge → 双插件 | 6.463 秒 | 32.973 秒 |
| 双插件原组合启动 | 2.416 秒 | 27.658 秒 |
| 双插件 → whale | 9.865 秒 | 25.306 秒 |
| whale 原组合启动 | 1.168 秒 | 15.974 秒 |
| whale → 原生 | 3.108 秒 | 18.276 秒 |
| 原生原组合启动 | 0.970 秒 | 15.115 秒 |
| 原生 → purge | 8.086 秒 | 32.928 秒 |

覆盖四种组合的日常启动及四个切换方向；不是所有可能切换方向和负载条件的穷尽测试。每个场景只测一次，没有用重复测量中的最快值替换样本。首次缓存格式升级的完整重建后台耗时 55.443 秒，成功启动，按用户允许的首次完整检查例外单独记录。

首个 purge 样本在 24.820 秒仍恢复历史，35.318 秒的补充观察已完整显示；完成点位于这个区间，不能认定刚好耗时 35.318 秒。后续改为每隔约 4 秒观察，共三帧，选取首次完整界面的帧；随后另行打开菜单确认响应。因此表内时间是**界面就绪的观察上界**，不是精确完成时刻，也不是同一时刻的交互延迟测量。后台响应仅代表启动请求已发出，不能替代窗口可用。首次建立缓存、文件变化或日志断档后的完整检查允许更慢。

公开阶段数据见 [startup-0.3.2.json](data/startup-0.3.2.json)。实际 Harness 截图包含私人会话，仅用于本机观察，不进入仓库。文档中的 [31 张功能演示截图](feature-tour-0.3.2.md) 使用真实前端和隔离演示数据，明确标注模拟状态，不能代替上述生产测量。

## 保留的历史失败记录

用户调整目标前，上一轮严格 30 秒验收失败：原生 → purge 的后台耗时 9.083 秒，在 31.098 秒仍显示 Loading plugins，37.864 秒观察到完整界面。另有 purge 日常启动观察值 30.875、30.950 和 55.078 秒，其中 55.078 秒样本的观察间隔较大。这些样本不能改写为严格达标，也不能据本轮单次观察保证不存在启动波动。

历史数据分别保留在 JSON 的 `previousStrictRun`、`previousIterationResults` 及修复前的 `preUsnFixRun`；本轮结果以 `results` 保存。严格 30 秒保证仍未建立，发布依据是用户明确放宽后的本机约 30 秒目标。

## 更新、空间与恢复边界

官方更新会改变旧补丁基线。0.3.2 在备份和大目录扫描前检查宿主身份，并在创建进程前再次检查；有变化则明确提示可能的更新或手动替换。相同内容的替换不会仅因文件时间或身份变化被拒绝。未完成事务遇到跨版本程序变化时保留恢复记录，停止把旧文件回放到新安装。详见[官方更新与冲突处理](host-updates.md)。本轮没有安装截图提示的 Harness 更新，也没有证明旧插件兼容新 Harness。

检查点、连续 USN 验证、有限校验缓存和只读推演索引已实现；校验和事务回滚继续保留。没有删除应用依赖或恢复对象来缩短时间。自动跨版本三方迁移、按引用清理历史对象属于后续设计，尚未实现。
