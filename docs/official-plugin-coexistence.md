# 在 Harness 内创建插件

[返回 README](../README.md) · [架构](architecture.md)

## 问题与修复

用户在 Harness 内升级一个自己编写的本地插件时，官方安装器因为另一个插件的构建授权而退出。停用插件只改变加载列表，包管理器仍会检查已经安装的依赖。旧策略同时留下了特殊插件的包名授权和待确认的 Git 来源授权，普通插件安装也因此收到 `ERR_PNPM_IGNORED_BUILDS`。

启动器现在按适配器登记表隔离特殊插件的构建脚本。普通安装保持这些脚本禁用，显式维护适配插件时才开放所选来源，完成后再次禁用。使用官方配置接口读写，先备份、再回读验证；不修改特殊插件的源码、版本或回滚记录。这是构建权限与文件归属的隔离，依赖仍由 Harness 的包管理器统一管理。

另一个问题是普通插件和用户设置被一并纳入了补丁限制。未经过启动器记录的普通插件现在显示为“由 Harness 管理”，当前配置可直接启动，停用后也可以继续切换其他已记录插件。用户配置文件只有与活动或待启用补丁发生路径重叠时才阻止切换，程序文件仍按已验证状态检查。停用的旧补丁不会冻结正常设置；再次启用该补丁时，原始内容不匹配仍会报告冲突。

原生配置检查也改为读取组件结构。旧实现把 YAML 里所有 `name` 都当成插件名，模型列表中的名称因此可能阻断切换。现在使用 Harness 自带的 YAML 解析器读取配置，只检查组件条目、插入项与组件组，不检查模型或提供商的显示名称。相同内容在当前进程内复用解析结果，不重复启动解析器，也不执行配置中的动态表达式。

## 实际验证

2026-11-04，在 Windows 和 Harness 0.2.1-rc.5 上进行了以下验证：

- 使用本机自带 pnpm 11.28.5，在离线临时项目复现构建授权错误；启用隔离后，同一普通本地插件安装成功，特殊插件的测试脚本没有执行。
- 使用 Harness 官方 CLI 安装用户已有的本地插件 1.0.1，退出码为 0，安装约 4.8 秒。
- 从启动器保留官方当前配置启动；官方插件页显示版本 1.0.1，组件状态为“运行中”。
- 安装前后，源码目录、purge 包内容及回滚记录、官方 EXE 和 ASAR 保持一致；257 项用户数据与外部源码条目比对无变化。

截图与原始日志保留在本机诊断目录，避免将用户源码路径、会话和私人插件内容上传到公共仓库。本轮验证安装和加载，不代替用户插件自身搜索、模型调用等业务功能的测试。

## 回归覆盖

自动化测试覆盖构建授权失败、超时、策略冲突、无关包权限保留、自制插件的当前配置启动、停用后的普通插件切换、用户配置变化，以及宿主与活动补丁被改动时的拦截。启动前脚本策略操作失败时，也会恢复刚才切换的插件组合。
