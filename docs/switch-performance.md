# 0.3.2 启动校验优化与文件数量说明

[English](switch-performance.en.md) · [完整功能截图](feature-tour.md) · [启动进度截图](launch-progress.md)

后续验收目标已调整为“约 30 秒”，历史的严格 30 秒结果仍保留，不改写为硬上限保证。最新回归和重启结果以[验证记录](validation-0.3.2.md)为准。

## 为什么会检查上万个文件

本机 dsh-purge 的实现会把官方 app.asar 解包为完整 resources/app，再修改其中部分文件。启动器通过固定的活动目录与暂存目录切换原生/补丁模式；一次开关不会新建一套编号递增的 app 副本。

2026-10-24 对保留的官方 ASAR 完整性表进行只读比较：

| 项目 | 文件数 |
| --- | ---: |
| 与归档比较的原有普通文件 | 12,967 |
| 内容相同 | 12,912 |
| 内容不同 | 55 |
| 额外新增 | 2 |
| 非联接范围内缺失 | 0 |

这些数字描述当前安装的差异，不能单独证明每项差异由哪个程序产生。runtime 是目录联接，校验视图记录链接本身，不继续遍历目标。先前遍历统计得到的 21,251 项包含该联接目标，不能当作本轮实际读取的普通文件数。因此，上万文件主要来自完整解包的应用与依赖，没有证据说明它们是反复开关堆叠出来的缓存。

校验缓存另存为本机数据目录下的 verification-cache.json，不属于补丁扫描根。删除它会使下次重新读取内容，不会减少应用需要保留的文件数。

最终格式 3 窗口复测后的统计为 14,648 项、2,750,036 字节，
对应 14,648 个不同文件标识，没有同一标识的旧版本重复项。原子写入配置等操作会产生新的文件标识，
因此条目数不要求完全不变；总量仍受 100,000 项上限约束。

另有 2 个目录检查点，共 17,375 个文件及目录条目；检查点上限为 32 个、总条目上限 100,000。检查点与逐文件缓存各有用途，不是额外的应用目录副本。

进度中的文件数包含元信息复核。缓存命中后仍会计数，但不会再次读取该文件的全部内容；不能用这个计数判断缓存是否生效。

## 已实现的优化

- 内置补丁持续停用时，普通插件切换不遍历未使用的内置暂存树。
- 已记录插件没有文件差异时，只修改加载配置；提交前验证当前组合，保留事务和失败回滚。
- 当前内容与已保存原生基线相同时，复用归档信息，避免重复逐条解析 ASAR；实际使用的恢复副本仍校验。
- 内容读取最多使用 32 个工作线程；只读推演中的目录指纹可在内容未变时复用。
- 只读视图移动子树时只更新受影响的父子索引，避免为一个文件的移动重建整个应用树索引。
- 本机 NTFS 上，核对卷编号、文件标识、创建时间、修改时间、ChangeTime、大小、当前日志身份与文件 USN，复用已验证的内容哈希。查询期间排除写入和替换，前后标识必须一致；元信息不可用、文件改变或缓存损坏时重新读取内容。
- 同一文件标识的旧校验记录自动淘汰，缓存最多保留 100,000 项；不删除应用依赖或回滚备份。
- 大目录以稳定目录身份和连续 NTFS USN 日志维护已验证检查点。整目录移位且内部内容未变时复用；内部变化、日志断档、未知记录或接口不可用则完整校验。
- 建立检查点时使用独占数据读取及 USN CLOSE 屏障，处理遗留句柄保留变更合并周期的问题；每次复用仍重新验证日志。路径和子目录索引最多复用两个位置，虚拟预演改动不能污染真实检查点。
- 输出索引来自独立验证后的快照，避免额外扫描吸收验证后才出现的外部改动。请求锁在响应发送前释放，慢客户端不阻塞下一次操作。
- 官方更新或手动替换宿主文件时，在备份和大目录扫描前提前拒绝，启动前再复核；不为一次必然失败的旧补丁切换创建新历史。见[更新与冲突处理](host-updates.md)。

缓存格式 3 使用 `GENERIC_READ` 数据读取权限并仅允许共享读取。属性权限句柄无法排除数据写入，
旧格式 1、2 缓存不再使用；升级后需完整建立一次新缓存。已有写者、打不开排他句柄或身份查询不可用时，
不能使用缓存命中来跳过读取。验证后的子树改动由连续变更日志及必要时的新一轮文件身份检查发现。目录检查点也采用格式 3，旧格式 1、2 不再复用。完整边界见[检查点设计](checkpoint-design.md)。

NTFS ChangeTime 包含文件变更信息，补充仅比较大小和 mtime 会漏掉的改动。参见 [Microsoft 的 FILE_BASIC_INFO 定义](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info)。这不等于抵御恶意篡改系统元数据或检测离线磁盘损坏的完整性证明。

## 验收口径与当前状态

本机目标已由严格 30 秒调整为“30 秒左右”。计时包含校验、组合切换与 Harness 自身加载；首次建立缓存、文件变化或 USN 日志断档后的完整检查允许更慢。后台响应不能代替窗口可用。

最终完整回归：Windows CI 的 Python 3.12、3.13 各 331 项测试全部通过，无跳过；32 项 JavaScript 测试均通过。随后正常重启启动器，在四种组合的日常启动及四个切换方向中，完整界面观察上界为 **15.115–35.318 秒**，之后菜单交互全部通过。

| 类别 | 后台阶段 | 完整界面观察上界 |
| --- | ---: | ---: |
| 原生、whale、purge、双插件原组合启动 | 0.970–2.643 秒 | 15.115–35.318 秒 |
| 四个组合切换方向 | 3.108–9.865 秒 | 18.276–32.973 秒 |

这些是最终代码的单次场景样本，不是所有环境的上限保证。旧严格验收中原生 → purge 在 31.098 秒仍加载的失败记录继续保留；更早的 0.3.1 whale 关闭后台操作曾达 189.297 秒，早期 0.3.2 首次 purge 缓存构建为 76.580 秒，均不混入本轮日常窗口时间。

详细场景、观察口径及历史数据见[验证记录](validation-0.3.2.md)。实现路径见[架构图与原理图](architecture.md)，[新版功能截图](feature-tour-0.3.2.md)使用隔离演示数据。校验、冲突检测和回滚保留，跨版本补丁自动迁移与历史对象垃圾回收尚未实现。
