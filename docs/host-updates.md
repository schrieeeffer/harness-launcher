# Harness 官方更新、校验与冲突处理

[返回使用指南](../README.md) · [检查点设计](checkpoint-design.md) · [版本验证记录](validation-0.3.2.md)

更新入口、混合更新和中断恢复的补充用例见[更新流程验证](update-validation-0.3.2.md)。

## 官方更新会不会被误判

更新会真实改变程序、ASAR 或依赖，因此旧补丁的基线可能不再适用。0.3.2 会保护性拒绝把旧记录直接应用到新安装；这不表示官方更新有问题，也不表示启动器已经证明它是恶意改动。

仅凭版本号或哈希变化，不能区分官方更新、手动替换和损坏。错误使用 `host_identity_changed`，明确提示“可能发生了官方更新或手动修改”，而不是声称已认证新版本。界面中的“新版本”提示只说明有更新可选；本次没有下载或安装该更新。

## 三种更新入口

启动器不控制 Harness 内的官方更新按钮，也不能拦截官方更新器退出后自行重启应用。以下保护发生在启动器的启动、切换、记录与恢复边界；不能据此保证第三方更新器永远不会出现问题。

| 场景 | 处理与边界 |
| --- | --- |
| 原生模式下检查或下载官方更新 | 下载到安装目录外且尚未替换受管文件，不会使当前基线失效。 |
| 原生模式下安装官方更新 | 可执行文件或归档变化后拒绝旧基线，不把新文件自动登记成旧版本；需要验证新版干净安装、重新适配插件。原生模式不是跨版本兼容承诺。 |
| 启用普通插件或 purge 时安装官方更新 | 可能留下旧解包目录、新归档和旧注入文件的混合状态。优先检查新活动归档，保留现场，停止旧补丁覆盖。应在更新前先退出 Harness、还原原生并重新启动原生环境，再使用官方更新。 |
| 普通插件自身更新 | 从“升级 / 重新记录”开始，先撤销旧层，再记录新版和首次运行。仅发布新记录后替换当前版本，旧内容与差异保留为历史。 |
| 记录窗口外更新插件或依赖，包括版本号不变的替换 | 启用或继续使用该插件时拒绝不匹配内容；先恢复旧包及依赖，再正确开始升级记录。不能在更新后补造旧基线。 |
| 已停用插件只更新包文件 | 受管原生文件未变时仍可原生启动；重新启用必须验证插件与依赖，不能套用旧快照。安装脚本若同时写了应用或注入文件，完整性检查仍会拦截。 |
| purge 自身更新 | 专用适配器不接受通用重新记录。先在旧版还原原生，新版本需兼容性适配及新快照。已停用 purge 的包版本变化不再无故阻塞保持原生的切换。 |
| 一次更新同时改动其他插件或共享依赖 | 暂停当前安装记录，保留快照与内容引用，避免把其他插件的改动归入本次插件。 |

不要同时进行官方更新和插件更新。官方更新失败或只完成一部分时，先由官方安装器恢复一致的安装；启动器不会通过覆盖旧快照“修好”一个未知的新旧混合版本。

本机已安装的 purge 版本还改写了官方更新入口：其辅助脚本会暂时移动解包目录、调用安装器并重启。已用隔离夹具覆盖这种中间状态：即使可执行文件和旧归档尚未改变，缺失的活动解包目录也不能被当作“组合未变”直接启动。插件更新脚本自身留下的恢复目录不属于可丢弃校验缓存，不会自动清理。本次只读取其实现，没有执行更新脚本或安装新版 Harness。

## 0.3.2 已实现的处理

在创建配置备份、扫描大目录或规划补丁之前，先检查已记录的宿主内容：

1. 对照当前组合及相关插件记录中的程序哈希；已不匹配时立即返回，不继续读取新 ASAR。
2. 程序相同则检查归档。purge 使用记录中的官方归档，查找顺序优先活动 `app.asar`，避免新归档被旧暂存归档遮蔽。普通插件可合法修改 ASAR，因此对照当前已验证组合中的活动归档，不拿原生归档误判它。
3. 相同字节被安装器复制或替换、仅文件时间变化，不当成宿主内容升级。新的 NTFS 文件身份会重新验证内容；相同大小、恢复修改时间的实际改动仍会被发现。
4. 提前检查相同并不等于批准启动。插件依赖、受管文件、预检后独立复核、提交与回滚检查仍执行；创建 Harness 进程前再次检查宿主，缩小更新恰好发生在切换提交之后的风险窗口。
5. 未完成事务在任何撤销写入前检查程序和三处归档位置。按事务游标在内存中推演合法的归档移动和写入，也覆盖“文件已移动但游标还未落盘”的中断；发现仅归档升级或新增活动归档时，同样停止回滚并保留事务日志和内容对象。
6. 创建进程前再次检查加载配置、所选插件及依赖、purge 安装包和宿主内容，拦截切换提交后才发生的包更新；不会因校验已完成而直接执行新版未知代码。
7. 安装会话在开始时固定三个归档位置的内容或缺失状态，并保存其他已安装插件及依赖的不可变包引用。安装前、首次启动前、退出保存和取消时重新核对，目标插件的正常升级可被记录，其他插件的同版本代码替换也会被发现。对象仍按内容去重，日常启动不增加这些安装会话副本。

安装期间把官方 ASAR 作为固定宿主边界。直接替换官方 ASAR 的插件不能通过这条通用记录路径；解包 app 内的普通文件改动仍可记录。不能仅凭“恰好在安装窗口内发生”就把宿主更新归属给插件。

新安装会话声明临时能力 `recording-update-guards`，不支持它的旧启动器会拒绝读取，避免降级后绕过保护。会话完成或确认未发生修改而取消后清除此能力声明；已有普通格式 3 记录继续可读。旧版未结束的安装会话缺少这些安装前证据，不能从现状补采；请先在建立会话的版本中完成或恢复，再升级启动器。

无变化时最多核验两个宿主内容锚点，不扫描整个应用目录、不创建新历史对象；已有可靠 NTFS 哈希缓存仍可复用。更新后的首次实际内容读取可能更慢，不把这一阶段伪装成零成本检查。其余文件和运行时依赖仍由原完整性流程验证，两个锚点不能代表整套安装都没有变化。

## 更新前后如何处理

更新前，先在旧版本上完全退出 Harness，使用启动器切换至原生组合，确认还原完成，并保留成套的安装与启动器数据备份。这能避免更新器面对正在启用的解包补丁，但不代表旧插件记录自动兼容更新后的程序。

若已经原地更新且出现宿主变化提示，保留旧记录，不要通过清空校验缓存、编辑版本号或强制还原旧快照来绕过。0.3.2 **没有自动跨版本迁移旧插件的功能**。兼容插件应在新版本的干净安装上重新记录；需要并行验证时，使用独立安装和独立启动器数据目录，不能让两套记录同时管理同一个应用目录。`migrate.py` 转换启动器数据格式，不会把旧补丁适配为新 Harness 补丁。

## 更低成本的后续设计（尚未实现）

增量迁移应以“旧官方基线 A、旧插件结果 P、新官方基线 N”比较每个插件实际涉及的文件，缺失文件也作为一种状态。先用内容身份排除无冲突项：

| 条件 | 文件候选结果 | 原因 |
| --- | --- | --- |
| P = A | 使用 N | 插件没有修改此文件 |
| N = A | 使用 P | 官方没有修改插件依赖的旧文件 |
| P = N | 使用 N | 双方结果已经相同 |
| 其他 | 保留冲突，生成待检查候选 | 双方对同一基线做了不同修改 |

文本候选可借鉴 [Git 三方合并](https://git-scm.com/docs/git-merge-file)；二进制、删除与修改冲突、移动路径、链接和共享文件需要明确规则。无文本冲突也不能证明程序接口兼容，仍须验证插件声明、入口与依赖，并在隔离安装中试运行。压缩后的 JavaScript 和结构化配置不宜机械地按行自动覆盖。

空间上应复用同一内容对象和基线索引，只新增变化文件与清单；当前内容库已在各自存储根内按 SHA-256 去重，但没有全局跨存储去重或 Git pack 压缩。purge 的完整解包运行目录仍有实际用途，不能当作多余缓存删除。

本轮最终窗口复测前的一次只读元数据统计中，当前记录库合计约 514.0 MiB，其中内容对象约 369.1 MiB，28 个事务计划约 116.6 MiB。逐文件校验缓存另约 2.2 MiB。统计未证明所有历史事务都可删除，也不包括原始应用与归档的全部空间；它说明后续应优先审查历史对象的引用和保留策略，而不是清空小型校验缓存。

后续清理应先计算引用关系：当前组合、保留的插件历史、必要回滚点、安装会话、迁移状态和未完成事务都作为保留入口。只有不可达对象经过宽限期后才可清理，维护过程应与写入互斥。Git 也提示立即清理与并发写入存在风险，见 [git gc](https://git-scm.com/docs/git-gc)。0.3.2 只淘汰可丢弃校验缓存的旧身份记录并限制容量，**没有自动删除恢复历史**。

这样把工作分成：日常验证变化证据、官方更新时一次重建基线并分析插件差异、空闲时按引用关系整理历史。它比每次全盘重扫或按时间直接删除旧备份更有明确的成本和恢复边界，但完整迁移与历史整理仍需单独实现和验收。
