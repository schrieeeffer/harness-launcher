# 0.4.4 启动速度实测

[返回 README](../README.md) · [校验原理](checkpoint-design.md) · [架构](architecture.md)

2026-11-04，在 Windows x64 上使用官方 Harness 0.2.1-rc.5 和 dsh-pet 0.4.1 测试。本轮只切换 pet；dsh-purge 1.1.90 一直保持关闭，未安装、升级或卸载它。

## 计时结果

| 场景 | 后台操作 | 观察到完整可用界面 |
| --- | ---: | ---: |
| pet 日常重启 | 13.6 秒 | **28.1 秒** |
| pet → 原生 | 15.3 秒 | **28.5 秒** |
| 原生 → pet | 14.9 秒 | **28.8 秒** |

计时从本机认证的 `/api/launch` 请求发出开始，该接口与首页启动按钮执行同一流程。每轮先通过 Harness 的“应用 → 退出”正常退出，再请求原组合或新组合。使用 Windows 窗口控制将主界面置前并截图，以完整输入区、工作区和模型选择器显示作为就绪点；另外实际输入并清空测试文字，确认响应，没有发送消息。没有把进程出现、加载画面或后台请求完成作为窗口可用。

窗口时间是观察到就绪的上界，包含工具读取窗口的耗时。表中为最终优化后的三个连续场景样本，使用已经建立的校验缓存，没有为计时清空缓存或下载插件，也未绕过官方加载流程。其他机器、插件组合和首次完整校验仍需分别测量。

## 找到的重复工作

旧流程中，安装包和依赖文件在同一次切换里多次扫描，还重复读取了没有参与切换的整套包恢复副本。pet 本身和其依赖合计包含近一万个恢复文件，数量来自依赖闭包，不能据此认定为反复开关产生了近一万个新增文件。

本次修改集中在通用读取与事务层：

1. 复用经过 NTFS 连续变更日志确认的插件目录索引；每次仍检查文件身份、目录变化和依赖路径。
2. 运行时与 CLI 分开检查，避免两套范围的 CLOSE 记录互相使缓存失效。
3. 只改加载配置的计划不再提前多扫一遍插件；执行前和启动前的检查保留。
4. 一轮依赖查找共用目录列表，读取结束后用新的列表重新解析依赖，检查新增遮蔽模块、可选依赖和路径变化。
5. 同一轮共享 ASAR 目录的 JSON 解析结果。每次仍读取实际目录字节；包内容、解包文件和完整性摘要继续检查。

6. 用户设置改变时，保留新设置，并复用内容相同的官方程序基线；不再因为模型或界面设置的变化而重新解析整份官方归档。组件配置使用官方 YAML 解析器读取，模型列表中的名称不再被误判为额外插件。

这些路径按文件与依赖结构选择，不按 pet 的包名分支。没有为此次计时调整 purge 适配器。

## 原生恢复与回滚

关闭 pet 后，对比同版本官方安装包：EXE、`app.asar`、三项 CLI 文件和受管理原生文件均一致；加载列表只有官方组件，没有活动的解包 `app` 目录。原生窗口可正常使用。

![关闭 pet 后的官方原生窗口](images/startup/native.jpg)

日常启动检查安装文件及恢复对象是否存在。真正使用补丁或恢复包时，仍读取并核对对应恢复文件的 SHA-256。事务日志、双向恢复内容和冲突检查保持有效；本轮未删除恢复材料或执行缓存清理。

## 自动化验证

针对性测试覆盖目录增删改、同大小且恢复修改时间的改写、目录替换、缺失恢复副本、依赖路径变化、新增遮蔽模块、可选依赖、日志失效、归档头变化和解包文件篡改。缓存不能把这些变化当作已经验证。

Windows CI 的 Python 3.12 和 3.13 两组各通过 543 项回归，前端 64 项测试通过。对应提交与结果可在 [Actions](https://github.com/schrieeeffer/harness-launcher/actions) 查看。维护界面、更新、卸载与完整检查点恢复的已有操作记录见[维护实测](maintenance-ui-validation.md)；本轮重点是启动路径，没有重做这些长时间维护操作。
