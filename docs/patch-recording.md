## 三种管理方式

启动器把每个已安装插件归入以下三类之一，界面上的标签和「补丁记录」的分组都基于这个分类：

| 类型 | 界面标签 | 关闭时 | 启用时 |
| --- | --- | --- | --- |
| **内置适配** | 支持自动还原补丁 | 使用保留的官方归档，暂存插件的注入文件 | 恢复同版本的补丁快照 |
| **通用记录** | 已自动记录补丁 | 按与安装相反的顺序撤销记录的文件差异 | 按安装顺序重新应用文件差异 |
| **未记录** | 未记录安装前状态 | 阻止组合切换，不能猜测原始文件 | 需先恢复干净安装，再通过启动器记录 |

没有安装前记录的插件**不会**被假定为没有补丁。只要存在这类插件，或者还原后 `cordis` YAML 中仍有手动添加的插件条目或动态表达式，「原生模式」就会拒绝宣称已经恢复到完整的官方状态。

## 一次切换做了什么

点击「启动 Harness」或「应用选择」时，启动器按以下顺序执行：

1. **前置检查**：Harness（包括托盘）已完全退出；应用路径有效；没有进行中的安装记录；记录范围内的文件没有在记录之外被改动；要启用的已记录插件版本没有变化。如果上一次切换中途中断，会先自动回滚未完成的部分，再请你刷新重试。
2. **并发检查**：`package.json` 自读取后没有被 Harness 或其他程序修改（比较内容摘要），否则要求刷新。
3. **备份**：把当前 `package.json` 原样保存到启动器数据目录的 `backups` 中。
4. **计算 bundle 列表**：`@deepseek-ai/dsh-base` 和 `@deepseek-ai/dsh-web-app` 始终保留；已有插件沿用原来的顺序；新启用的插件追加到末尾。`package.json` 中的其他字段原样保留。
5. **整套预检**：在只读文件视图中推演撤销当前通用层、切换内置适配器、应用目标通用层的全过程；核验原生基线、插件与依赖内容、双向文件副本、目录结构和目标文件哈希。此时不修改应用与 profile 文件，也不另建整套临时应用目录。
6. **再次检查**：执行前重新核验程序、插件包与依赖、记录索引及所有输入文件的内容。预检后出现改动就停止。
7. **统一事务**：保存不可变操作计划和小型位置日志，再依次撤销当前层、切换内置层与 bundle 配置、应用目标层。独立插件共用的目录由组合单独管理；全部关闭时清理这些额外目录。
8. **验证与登记**：核验实际结果与整套目标组合完全一致，保存目录指纹、原生基线引用及组合记录，最后写入提交标记。
9. **启动**（仅「启动 Harness」）：以 `DSH_HOME` 指向当前数据目录启动 Harness。

预检不通过时不会开始修改实际文件。执行或启动失败时，按反向操作恢复切换前的文件、配置和组合索引。进程中断后能从日志位置恢复，包括文件已写入但位置尚未更新、恢复过程再次中断等情况；遇到中断后的未知改动会停止覆盖并保留日志。

切换不会触碰账号、会话、插件依赖和普通偏好；原生模式不是清空用户数据。关闭插件也不会卸载它，插件仍然保留在 `node_modules` 和 `dependencies` 中，下次可以直接启用。新增插件的兼容性和相互依赖仍然由插件和 Harness 负责。

## dsh-purge 内置适配器

dsh-purge 会修改应用本体，因此使用一个专用适配器，而不是通用记录：

- **首次核验**：依次查找安装目录中的 `app.asar`、当前安装与数据目录对应的暂存 `official.asar`、`app.asar.bak`，核验归档内置的完整性信息，并记录版本和哈希。即使补丁记录缺失，也能识别启动器此前暂存的官方归档；仍须通过完整性和补丁目录版本检查才能重新建立记录。
- **关闭时**：把 `resources\app` 暂存到安装目录内一个独立的目录，改用官方 `app.asar`；插件的提示词、已识别的注入规则、红队预设和 CLI 路径一起还原。
- **启用时**：恢复之前捕获的同版本补丁目录和注入文件，**不会**重新执行可能修改其他安装的补丁脚本。
- **日志与回滚**：组合切换的统一事务同时覆盖内置适配和通用记录；任一步骤失败都会回滚，中断后下一次操作会先恢复。运行时只使用新版统一日志；有旧日志时先在原版本完成恢复，再迁移。
- **版本变化**：应用或插件升级、文件被外部修改、目录冲突，或找不到官方归档时，停止覆盖并报告原因，不会把旧补丁套到新应用上。升级后需要在当前版本上重新应用插件并建立新的快照，旧快照会保留以便核查。

格式 3 的解包目录与预设记录必须具备内容哈希，可识别保留时间戳的改动，也不会因纯时间戳变化误报。旧记录只能由离线转换器先核验原有证据，再建立内容身份；运行时没有回退到元数据身份的分支。目录移动事务同时记录内容指纹，中断恢复时也会检查。原始归档和重放的文件内容同样使用内容哈希校验。dsh-purge 的安装内容和 Harness 提供的 SDK 也会留存版本关联；SDK 绑定到已保留的官方归档。dsh-purge 不能通过「手动添加」做通用记录，它的升级也不走「升级 / 重新记录」；Harness 本体升级后同样需要重新校验官方基线。

## 通用安装记录

### 流程

1. 安装**之前**打开「手动添加」，填写准确的插件包名。
2. 选择来源：npm 包（可填版本或标签）、本地目录、Git 仓库地址，或「自行安装」。启动器先建立快照，再通过 Harness 官方 dsh CLI（`plugin --profile desktop add <来源>`）安装；选择「自行安装」时，在快照完成后自己在 Harness 内安装。
3. 备份和安装完成后自动打开 Harness，正常使用这个插件即可；首次运行产生的文件变化也会计入记录，不需要专门点击“试用完成”。
4. 完全退出 Harness（包括托盘）后，后台确认进程已退出并连续至少 2 秒没有文件元数据变化，再自动扫描和保存。保存前重新校验整个范围、插件列表与版本、加载组合和 Harness 可执行文件哈希，校验还原和重新应用的文件副本。没有常规手动扫描、复核或保存按钮。

服务每秒监督一次安装会话，关闭浏览器不影响继续记录。未观察到程序运行时不会猜测首次运行已经完成，启动后 30 秒仍未检测到运行会暂停；进程观察是 Windows 上的保守检测，不等同于插件功能测试。

如果安装器失败，安装前快照会保留，可以修复问题后继续记录；安装器的输出保存在 `patches\<标识>\tracking\logs` 中。如果安装结果中找不到你填写的包名，记录会停止并提示检查来源。

### 记录范围

| 范围名 | 位置 | 说明 |
| --- | --- | --- |
| `app` | `<安装目录>\resources\app` | 解包后的应用目录 |
| `archive` | `<安装目录>\resources\app.asar` | 应用归档 |
| `archive_backup` | `<安装目录>\resources\app.asar.bak` | 归档备份 |
| `unpacked` | `<安装目录>\resources\app.asar.unpacked` | 归档外的原生文件 |
| `cli` | `<安装目录>\resources\runtime\cli` | 命令行运行时 |
| `agents` | `<数据目录>\AGENTS.md` | |
| `claude` | `<数据目录>\CLAUDE.md` | |
| `prompt` | `<数据目录>\prompt-inject.md` | |
| `rules` | `<数据目录>\rules` | |
| `skills` | `<数据目录>\skills` | |
| `presets` | `<数据目录>\.agent-presets` | |
| `user_yaml` | `<数据目录>\profiles\desktop\cordis.patch.yml` | |
| `root_yaml` | `<数据目录>\profiles\desktop\cordis.yml` | |

异常页面的改动清单和导出的 JSON 中，每个文件写作 `范围名|相对路径`，`|.` 表示范围本身。例如 `skills|desk-pet/SKILL.md` 就是 `<数据目录>\skills\desk-pet\SKILL.md`。启动器自己的 `.harness-launcher-*` 暂存目录不会被记录。

### 默认排除

账户凭据、会话、附件和缓存不在文件补丁记录范围内。`node_modules`、`package.json` 和 lock 文件不作为普通补丁层切换；新版另存插件包与可解析依赖的安装内容、依赖关系及 profile 安装元数据，作为版本恢复材料。关闭插件不会卸载或重装依赖，也不会恢复整个 profile。

### 链接与特殊文件

目录中的链接（包括 Windows 联接点）只记录指向的目标，不跟随读取外部路径。如果在记录窗口内新增或修改了链接，或者某个路径在文件和目录之间互换，启动器会拒绝自动登记。遇到其他不支持的文件类型时也会停止。

### 归属与自动校验

记录的是**一个时间窗口内**的文件差异，而不是进程审计；自动校验不能证明某个写入来自哪个进程。期间只操作这个插件，不同时编辑其他文件。检测到其他插件安装、删除、升级或组合变化时拒绝登记；扫描后的新文件和改动同样会阻止保存。范围内稳定的手动修改仍可能被包含，不能把自动记录称为完整的进程归属审计。

正常记录自动保存。安装失败、启动失败、文件仍在写入或校验失败时，原始基线保留不变，处理问题后点击「继续自动记录」。进程崩溃或服务重启后，未完成会话先进入异常状态，不会悄悄把服务停止期间的文件当成插件改动；继续时重新观察运行或重新扫描。旧版未完成会话应先在原版本结束，再运行迁移工具。

取消仅允许于插件列表未改变、原始文件也没有改变的会话。发生安装或文件改动后不能取消记录。启动器不会自动卸载插件或删除已安装依赖。

### 共享文件、叠加与基础组合

多个插件改同一个文件时，启动器会检查基线哈希，不强行合并。如果某个插件是在另一个补丁插件改过的文件基础上记录的，「补丁记录」会显示**记录时的基础组合**；启用它时可能需要同时选择原有的基础组合，或者在新的基线上重新记录。完全关闭时，相互独立或可以叠加的记录层会按相反顺序依次撤销。

### 升级与重新记录

已记录的插件升级时，在「补丁记录」中点击「升级 / 重新记录」，选择新版来源（例如 npm 版本），也可以保持「自行安装」，之后在 Harness 内升级。

- 开始时先确认并保留当前版本的安装内容与依赖，再撤销旧的记录层，建立新的文件基线。
- 新版安装与首次运行完成并自动校验通过后，才替换当前记录；旧版安装内容、依赖、差异索引和不可变版本引用保留为历史，新版本指向前一版本。
- 新版本不再写入的旧文件不会沿用。
- 校验期间如果版本再次变化，会暂停保存，处理后继续会重新扫描。
- **必须在升级之前开始记录。** 绕过启动器直接升级、运行后在记录之外新增的补丁，或其他外部修改，都会触发保护，启动器不会自动推断或保证还原。

已安装但没有记录的插件，不能靠安装后的快照补回未知的历史改动，启动器会拒绝为它开始记录。

## 插件版本与组合记录

- **插件版本**：新版通用记录把安装来源、实际版本、安装前后快照、文件差异、基础组合及其版本引用关联到一个按内容哈希命名的不可变记录。已安装包与依赖按依赖图留存文件，记录必需、可选及 peer 依赖和现有 lock 文件；重复内容复用同一份 blob。缺少必需依赖、包内容仍在变化或出现不支持的嵌套链接时暂停保存。
- **一次性迁移**：0.3.0 的 `migrate.py` 只接受完整 v2 数据，在独立同级 stage 转换并核验对象、文件副本与组合，然后将完整旧根目录改名为 `.archive-*` 并切入新根目录。设置、登记表、适配状态、切换日志和配置备份统一为格式 3，运行时不读取归档或旧格式。不可变内容对象维持各自既有契约；缺失历史与未完成操作会阻止迁移。目录切换中断由 `--recover` 处理，不改 Harness 文件。详见 [架构与数据契约](architecture.md)。
- **原生基线**：按 Harness 可执行文件哈希区分，保留撤销所有已知补丁后的托管文件内容及官方归档信息。每次组合都必须能够回到同一基线；额外的 `app.asar.bak` 不作为正在使用的官方基线。账户、会话和安装依赖仍保留。
- **组合记录**：保存插件实际版本、不可变版本引用、通用层顺序、最终 bundle 顺序、原生基线和预期文件内容。相同结果复用记录，切换失败不会把目标组合登记为当前组合。
- **方案与备份约束**：新保存的方案和配置备份会约束插件版本、记录引用和 Harness 版本，使用时发现变化就停止，请检查后重新保存方案。v2 迁移保留既有版本锁，只重写确实转换的对象引用，不重新绑定到当前版本。便携方案导入则明确绑定本机当前版本。导出格式不变，仅分享插件包名，不分享本机版本库或个人路径。

这一阶段提供版本留存与可靠的当前版本组合切换，尚未提供安装历史版本的一键降级入口，也不自动合并文本或二进制补丁。配置备份仍不是完整插件降级；真实文件冲突会在预检时报告，不能据此宣称任意插件组合都兼容。

## 保护与恢复机制

- **目录指纹**：保存记录或完成切换后，启动器会记录托管范围的目录指纹。下一次切换前发现文件时间戳变化时，会用当前组合或匹配的最近安装快照核对内容哈希；例如 Harness 重写内容相同的 `cordis.yml` 不再阻止切换。新增、删除、内容变化或缺少可信快照仍会停止自动覆盖，检查不会改写文件或把现状重新记为基线。
- **原始内容核对**：准备整套切换或下一次安装基线时，还会把已读取的完整内容与可信历史快照比较，防止同大小、同时间戳的未知改动成为新的原生基线或安装前状态。
- **切换中断**：整套操作计划只保存一次，小型日志逐步更新位置并记录最终提交状态。中断后的下一次操作会先回滚，再请你刷新重试；已经提交的事务只清理日志。恢复过程中也保留位置，未知改动会阻止覆盖。恢复完成之前不能开始新的安装记录。
- **完整校验与去重**：自动记录会读取文件内容校验哈希，保存前再次读取整个范围，原始与改动后的副本都校验通过才登记。副本按哈希去重；文件较多时可能较慢。重放在覆盖第一个文件前先校验整个操作序列需要的双向副本。
- **后台任务**：备份、安装、首次运行监督与保存均在后台执行，关闭菜单仍继续。服务不再依据网页心跳缺失退出；通过设置中的「退出启动器后台」显式结束，进行中的写入或记录会阻止退出。异常在磁盘保留，下次打开处理。原始基线不因重试而被替换。

## 存储位置

快照和状态保存在 `%USERPROFILE%\.harness-launcher\patches\<标识>\` 中，`<标识>` 由 Harness 安装目录和 Harness 数据目录共同计算得出。运行数据独立于源码目录；可用 `--data <目录>` 指定其他位置，切勿只移动索引而丢下 blob 和暂存目录。默认位置避开 Windows 商店应用的 AppData 虚拟化；新版不再自动搜寻或合并旧 AppData。自定义完整 v2 目录使用 `migrate.py --data <目录> --apply` 离线转换：

| 路径 | 内容 |
| --- | --- |
| `state.json`、`blobs\` | 内置适配器的状态、恢复日志和文件内容 |
| `tracking\registry.json` | 通用记录的索引、历史和当前会话 |
| `tracking\blobs\` | 按内容哈希保存的文件副本 |
| `tracking\snapshots\`、`tracking\deltas\` | 快照和差异清单按内容哈希保存，读取时进行领域结构校验 |
| `tracking\packages\`、`tracking\revisions\` | 插件及依赖内容清单、不可变插件版本 |
| `tracking\baselines\`、`tracking\combinations\` | 原生基线、安装前配置及组合记录 |
| `tracking\transactions\`、`tracking\switch.json` | 不可变整套切换计划、进行中的事务位置 |
| 同级 `<数据目录>.archive-*` 及 `.manifest.json` | 完整旧数据目录与校验清单，仅供离线恢复 |
| 同级 `<数据目录>.upgrade.json`、`.stage-*` | 目录切换日志及独立暂存目录；中断时保留并运行 `--recover` |
| `tracking\logs\` | 官方安装器的输出 |

当前没有启用的文件会暂存在安装目录的 `resources\.harness-launcher-<标识>` 和数据目录的 `.harness-launcher-<标识>` 中，里面可能保存着官方归档、插件目录和预设。**不要手动删除这些目录。**

## 不在范围内的内容

注册表、系统服务、驱动、网络端的更改、其他安装，以及上述范围以外的目录都不会被记录或还原。自动记录不等于整台电脑的系统还原。

## 移除启动器

1. 先选择你想最终保留的模式，并点击「应用选择」。
2. 删除启动器的快捷方式和源码不会回滚任何应用文件。
3. 仍然保存着非激活版本的 `.harness-launcher-*` 暂存目录和 `patches` 快照，删除后就不能再切换回这些版本。请确认不再需要后再删除。
