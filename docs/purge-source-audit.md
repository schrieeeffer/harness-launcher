## 已复现的上游配置错误

问题位于 [`lib/profile-insert.js` 的解析和重写函数](https://github.com/YuJunZhiXue/dsh-purge/blob/160b9114cbad7beca3d4d3f9f027ec843bf46f5e/lib/profile-insert.js)：

- `parseAllowBuildLine` 会把未加引号的网址中 `https:` 的冒号识别成 YAML 键值分隔符。
- 固定提交的授权键被截为 `dsh-purge@https`，完整提交信息丢失。
- 重写时又追加包内声明的 master 地址；下一次重写再次截断，产生重复键。
- 即使输入的完整网址加了引号，输出函数也会去掉引号，不能保证重复执行后结果不变。

安装脚本调用此函数；插件加载后的自修复也会调用。因此第一次安装结束并不保证配置在首次运行后仍然有效。本机 profile 中确实出现了重复的截断键。

在隔离目录中，使用上游原函数处理合成配置，再调用官方 pnpm 的只读 `list --depth 0 --json`：

| 输入状态 | 固定提交信息 | pnpm 退出码 | 结果 |
| --- | --- | --- | --- |
| 原始配置 | 保留 | 0 | 正常读取 |
| 调用一次重写函数 | 丢失 | 0 | 尚能解析，但授权键已改变 |
| 调用两次重写函数 | 丢失 | 1 | `duplicated mapping key` |

这能解释后续包管理操作被配置错误阻止。它不能单独证明当前 Harness 窗口崩溃，也不是前两次安装失败日志中 `EPERM` 或 `ERR_PNPM_IGNORED_BUILDS` 的替代解释。

## 修复边界

上游应正确处理 YAML 键、保留完整来源和原有授权决定，并增加重复执行结果不变的测试。已经丢失的固定提交信息应从可验证的安装记录恢复，不能猜测或改为允许全部脚本。

启动器侧适合增加通用的包管理配置检查：覆盖安装前、安装后和首次运行结束，明确指出损坏文件和具体错误，保留原文件与恢复检查点。该机制应适用于所有插件，不按 purge 名称绕过校验或伪装为已完成。

2026-10-28 一轮只完成源码调查与隔离复现，未修改已安装的第三方源码或实际宿主文件；上述防护建议尚未因此成为已发布功能。
